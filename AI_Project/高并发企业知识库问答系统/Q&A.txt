A：好的，我的 RAG 系统分为三个核心层次：

第一层：数据处理层

从 PDF、DOCX、PPTX 等多种格式的文档中提取文本
使用语义分块（semantic chunking）将长文档分成 512 字符的块

语义检索（FAISS）- 捕捉语义相似性

LLM 重排序 - 智能融合多维度信息

将检索到的相关文档作为上下文

模型在这个上下文基础上生成回答
每个回答都标注了参考文档，保证可追溯性
性能指标：

初始化：3-5 秒

4️⃣ 问题：你说缓存优化提升了 97% 的响应速度，具体是怎么实现的？
面试官想了解： 你的优化思路、是否真的理解缓存的原理

高分回答：

这是我项目中最自豪的优化。我实现了两层缓存架构：

第一层：Embedding 缓存（最关键）

问题：每次查询都要调用 DashScope API 对用户问题进行向量化，这很耗时
解决方案：缓存已经向量化的文本
实现方式：
用户问题 → 计算哈希值 → 查询缓存
如果命中 → 直接返回向量
如果未命中 → 调用 API → 存入缓存
命中率：60-70%（因为很多用户会重复提问）
成本节省：减少 70% 的 API 调用费用
第二层：查询结果缓存（LRU）

问题：即使 Embedding 缓存命中，检索和生成还是需要时间
解决方案：缓存完整的查询结果
实现方式：
用户问题 → 查询结果缓存
如果命中 → 直接返回结果（<100ms）
如果未命中 → 执行完整流程（3-4 秒）
命中率：30-40%
响应时间：<100ms vs 3-4 秒，性能提升 97%+
缓存命中的场景：

用户重复提问同一个问题
相同的技术参数查询（比如都查"ADS6311"）
常见的故障排查问题
性能对比表：

操作              无缓存    有缓存    提升
─────────────────────────────────────
初次查询          3-4秒     3-4秒     0%
重复查询          3-4秒     <100ms    97%+
平均响应时间      3.5秒     0.5秒     85%+
实现细节：

使用 Python 的 functools.lru_cache 装饰器
自定义 Embedding 缓存管理器
支持缓存持久化（可以保存到 Redis 或本地文件）
缓存大小限制为 1000 条记录，防止内存溢出

这是一个很细节的问题，但很重要。文档分块的方式直接影响检索质量。

我的分块策略：

向量表达不够精准
可能包含多个不相关的主题
检索时容易引入噪音
512 字符的优势：
既保证了上下文完整性
又保证了向量精准度
实验表明这个大小的准确率最高
具体实现：

python
1. 按段落分割

8️⃣ 问题：BM25 算法是什么？为什么用它做关键词检索？
面试官想了解： 你对信息检索基础理论的理解

高分回答：

BM25 是一个经典的信息检索算法，我用它来做关键词检索。

BM25 的原理：

BM 是 Best Matching 的缩写
它结合了 TF（词频）和 IDF（逆文档频率）
公式大概是：
score = IDF(q_i) * (f(q_i, D) * (k1 + 1)) / (f(q_i, D) + k1 * (1 - b + b * |D| / avgdl))
其中 k1 和 b 是可调参数
为什么用 BM25：

经过验证 - 这是一个经典算法，在信息检索领域被广泛使用
对技术参数敏感 - 对于"ADS6311"这样的专业术语，BM25 能精准匹配
计算快速 - 不需要调用 API，本地计算，速度很快
与语义检索互补 - 语义检索处理语义相似性，BM25 处理精确匹配
与其他方案的对比：

TF-IDF：更简单，但对词频的惩罚不够
BM25：更复杂，但效果更好
神经网络排序：效果最好，但需要训练数据和计算资源
在我的项目中的应用：

对每个查询，我同时执行 BM25 和语义检索
BM25 返回关键词匹配度最高的 top-10 结果
语义检索返回语义相似度最高的 top-10 结果
然后用 LLM 对这 20 个结果进行重排序，取 top-5

效果：API 调用成本减少 70%，响应速度提升 97%
难题4：混合检索的融合方式

问题：语义检索和 BM25 检索返回的结果如何融合？
原因：两种方法的分数范围不同，不能直接比较
解决方案：
先对两种方法的分数进行归一化
然后用 LLM 对融合后的结果进行重排序
最后取 top-5 的结果
效果：准确率从 80% 提升到 85%，召回率从 75% 提升到 88%
1️⃣4️⃣ 问题：你为什么选择 Streamlit 作为前端框架？

高分回答：

我选择 Streamlit 主要是因为以下几个原因：

Streamlit 的优势：

快速开发 - 用 Python 写前端，不需要学 JavaScript、HTML、CSS
自动热更新 - 修改代码后自动刷新，开发效率高
内置组件 - 有很多现成的组件（输入框、按钮、图表等）
数据可视化强 - 对 Pandas、Matplotlib、Plotly 的支持很好
部署简单 - 可以直接部署到 Streamlit Cloud，不需要配置服务器
与其他方案的对比：

Flask + HTML/CSS/JS：功能更强大，但开发复杂，需要前端知识
Django：功能最强大，但对于这个项目有点过度设计
Gradio：也很简单，但组件不如 Streamlit 丰富
FastAPI + Vue：性能最好，但开发复杂
为什么 Streamlit 最适合：

这是一个 AI 应用，主要关注功能而不是界面美观
快速原型开发很重要
用户主要是技术人员，对界面要求不高
团队只有我一个人，需要快速开发
Streamlit 的缺点和我的解决方案：

缺点：性能不如传统 Web 框架
解决方案：加缓存，优化检索算法
缺点：自定义程度低
解决方案：使用 Streamlit 的高级特性（st.session_state、st.cache_data）
